# Touch Bridge 심사 요약서

## 1) 문제와 대상
- **대상**: 시각장애인/저시력 사용자
- **문제**: 평면 터치패널 가전(전자레인지, 세탁기, 인덕션 등)은 버튼 위치를 손끝으로 더듬어 찾을 수 없다. 물리 버튼·점자 라벨이 없는 가전이 빠르게 늘면서, 시각장애인은 신제품을 살 때마다 "이 가전을 내가 혼자 쓸 수 있는가"부터 다시 확인해야 한다.
- **현재 대안의 한계**: 음성 인식 스피커형 스마트홈 가전으로 교체하려면 비용이 크고, 이미 집에 있는 가전은 그대로 못 쓴다. Touch Bridge는 **교체가 아니라 부착**으로 기존 가전을 그대로 접근성 있게 만든다.

## 2) 해결 방식
- 사용자가 음성 또는 수동 입력으로 명령을 내린다.
- 앱이 명령을 논리 버튼 시퀀스(`BT-xx`)로 변환해 BLE로 ESP32 허브에 전송한다.
- 하드웨어(NK1704S 42각 스텝모터 기반 XYZ 구조)가 실제 터치패드를 물리적으로 눌러 동작을 수행한다.
- 즉, 사람이 "말하면" 로봇이 "대신 누른다" — 시각 확인이 필요한 마지막 단계를 하드웨어가 떠맡는다.

```text
사용자 음성/탭
  -> 앱: 논리 버튼 ID(BT-xx) 결정
  -> 앱: 저장된 매핑으로 X/Y/Z 명령 변환
  -> BLE(향후 Wi-Fi) -> ESP32 -> UART -> Arduino Uno(GRBL)
  -> TB6600 -> NK1704S XYZ 구조가 물리 버튼 누름
  -> GRBL 응답(ok/error/ALARM) 역방향 회신
  -> 앱: 사람의 말로 번역해 음성 안내
```

### 2-1. 하드웨어 구성과 선택 이유

상세 내용은 [HARDWARE_MIGRATION_PLAN.md](HARDWARE_MIGRATION_PLAN.md)를 따른다.

| 구성 | 선택 | 이유 |
|---|---|---|
| 모터 | NK1704S 42각 x3 | 매핑 좌표를 매번 같은 자리로 이동하기 위한 반복 위치 정밀도 |
| 드라이버 | TB6600 x3 | 전류 설정으로 모터 보호, 가격/수급 균형 |
| 전원 | 12V 분리 공급 | 로직 전원과 분리해 노이즈와 MCU 리셋 방지 |
| 제어 | Arduino Uno + GRBL | 가감속, 리미트, ALARM 안전 상태를 검증된 펌웨어에 위임 |
| 무선 | ESP32 BLE, 향후 Wi-Fi | 무선 계층만 분리해 개발 위험 최소화 |

핵심은 모션 제어와 안전 정지를 GRBL에 위임하고, 앱은 "의도를 안전하게 명령으로 만드는 일"에 집중하는 것이다. 저렴하고 구하기 쉬운 부품 구성은 접근성 제품의 보급 가능성과도 연결된다.

## 3) 접근성 UX 중심 설계 — 핵심 차별점

### 3-1. 시각장애인 우선 정보 구조
- 모든 화면은 진입 시 "화면 이름 → 현재 상태 → 가능한 다음 행동 1개" 순서의 TTS로 시작한다. 화면을 한 번도 보지 않고도 다음에 뭘 해야 하는지 알 수 있다.
- 홈 화면은 현재 활성 기기명과 연결 상태를 가장 먼저 음성으로 알려주고, 큰 "말하기" 버튼 하나로 음성 명령을 시작하게 한다. 기기 선택을 위해 여러 단계의 탭을 누를 필요가 없다.
- 자세한 문구 원칙과 화면별 추천 TTS는 [ACCESSIBILITY_COPY_GUIDE.md](ACCESSIBILITY_COPY_GUIDE.md)에 정리했다.

### 3-2. 보호자 모드 — 구조 변경과 일상 사용의 분리
- 시각장애인 사용자가 화면을 보지 않고 실수로 기기를 추가/삭제하거나 매핑을 깨뜨릴 위험을 원천적으로 차단한다.
- **사용자 모드**(기본값): 홈, 비상 정지, 설정만 보인다. 가전을 "쓰는" 데 필요한 것만 남긴다.
- **보호자 모드**(가족/시설 관리자가 ON): 기기 관리(추가/삭제/연결/매핑)가 하단 바에 나타난다. 새 가전을 들였을 때만 켜고, 평소엔 꺼둔다.
- **개발자/시연 모드**: BLE 원본 로그, raw 명령, 조이스틱 등 디버깅 도구는 보호자 모드에서도 기본적으로 숨기고 별도 진입이 필요하다. "보호자가 실수로 가전을 이상하게 움직이는" 사고까지 한 단계 더 막는다.
- 이 3단계 분리는 단순한 메뉴 정리가 아니라, **시각 확인 없이 안전하게 쓰기 위한 안전장치**다.

### 3-3. 오작동 방지 — 이중 확인 구조
- 모든 실행성 액션은 "첫 탭 = 안내, 둘째 탭 = 실행"의 이중 탭 확인을 거친다. 화면을 보지 않는 사용자가 잘못 짚은 버튼을 즉시 실행시키지 않는다.
- 음성 명령도 모호하거나 위험한 경우(여러 기기 후보, 활성 기기 불명확 등)에는 즉시 실행하지 않고 되묻는다 — "전자레인지 30초"처럼 기기명이 명시되면 바로 실행하되, 불확실할 때만 확인 질문으로 전환한다.
- 첫 탭/실행/실패는 서로 다른 진동 강도와 패턴으로 구분되어, 사용자가 소리를 놓쳐도 손끝 감각으로 상태를 알 수 있다.

### 3-4. 비상 정지 — 항상 최우선
- 비상 정지는 어떤 모드(사용자/보호자/개발자)에서도 하단 바에서 사라지지 않는다.
- "멈춰", "정지", "그만", "중단", "stop" 음성 명령은 어떤 화면, 어떤 작업 중에도 다른 모든 처리보다 먼저 인식되고 즉시 실행된다.
- 3초 홀드 비상 정지는 진행 중 진동과 완료 TTS("즉시 중단했습니다. 기기가 멈췄습니다.")로 끝까지 상태를 알려준다.
- 화재·과열·끼임 같은 실제 위험 상황에서, "화면을 봐야 멈출 수 있는" 인터페이스는 시각장애인에게 의미가 없다는 전제에서 설계했다.

### 3-5. 기존 가전의 접근성 개선 — 교체가 아닌 부착
- 새 스마트 가전을 사는 대신, 이미 집에 있는 전자레인지 등에 하드웨어를 부착해 그대로 쓸 수 있게 만든다.
- 기기별 버튼 배치(2x2, 3x3 등)는 사진 매핑 + AI 분석으로 등록하므로, 모델마다 다른 패널 구조에도 동일한 구조로 대응한다.
- 저장된 매핑이 없을 때만 검증된 데모 좌표로 동작하는 fallback 구조라, 시연 안정성과 실제 제품 확장성을 동시에 확보했다.

### 3-6. 앱-하드웨어 연동의 차별점
- 앱은 "안전하게 명령을 만드는 일"만 책임지고, 하드웨어는 "물리적으로 누르는 일"만 책임진다 — 책임이 명확히 나뉘어 있어 펌웨어/앱 어느 쪽이 바뀌어도 다른 쪽 구조를 흔들지 않는다.
- AI(Gemini)는 좌표를 직접 만들지 않고 논리 버튼 ID만 생성한다. 좌표 변환은 기기별 저장된 매핑이 전담하므로, AI의 환각이 곧바로 잘못된 물리 동작으로 이어지지 않는다.
- API 키 등 민감 정보는 백엔드에만 보관하고 클라이언트에는 두지 않는다.

## 4) 현재 구현 상태(심사 기준)
- 완료
  - BLE 연동 1차: 스캔/연결/명령 전송
  - 음성 명령 파싱 및 전송 연계
  - 하단 내비게이션 접근성 재설계: 독립 음성/연결 탭 제거, 홈 말하기 액션 및 비상 탭 상시 노출
  - 보호자 모드 접근 제어: 기기 추가/연결/매핑/개발자 도구를 모드별로 격리
  - 접근성 실험 지표 수집(완료율/평균시간/비상정지/타임아웃)
  - 테스트 자동화 통과 (flutter analyze / flutter test)
- 고도화 예정
  - BLE 재연결 안정화
  - 센서 피드백(전류/온도) 수집 및 상태 모니터링
  - TTS 문구 전수 적용 및 실사용자 검증 (현재 후보 문구: [ACCESSIBILITY_COPY_GUIDE.md](ACCESSIBILITY_COPY_GUIDE.md))

## 6) 예상 질문과 답변

**Q. 버튼 위치가 어긋나거나 기기가 밀리면?**

A. 장치와 가전은 고정 설치 전제다. 보호자 모드의 테스트 터치로 검증 후 저장하고, 어긋나면 기준점(0,0)부터 재매핑한다. 카메라 기반 자동 보정은 향후 과제다.

**Q. 안전은 어떻게 보장하나?**

A. 3겹 구조다. 앱은 이중 탭 확인, 음성 "멈춰" 최우선, 3초 홀드 비상 정지를 제공한다. 펌웨어는 GRBL의 리미트/ALARM 정지를 사용한다. 물리적으로는 12V 모터 전원 분리와 수동 차단을 둔다.

**Q. AI가 잘못 판단하면 기계가 엉뚱한 곳을 누르지 않나?**

A. AI는 논리 버튼 ID까지만 만들고 좌표는 만들지 않는다. 실제 좌표는 보호자가 검증·저장한 매핑에서만 나오므로, AI 오류가 곧바로 임의의 물리 동작으로 이어지지 않는다. 모호하면 되묻는다.

**Q. BLE가 끊기거나 명령이 유실되면?**

A. 명령과 응답 확인 기반으로 순차 전송하고, 실패는 즉시 음성으로 알린다. 연속 전송과 통신 유실은 [REPRO_RUNBOOK.md](REPRO_RUNBOOK.md)의 통신 검증 절차로 확인한다.

**Q. 왜 ESP32 하나로 통합하지 않고 Uno+GRBL을 유지하나?**

A. 검증된 모션 제어를 유지하면서 무선 계층만 추가하는 것이 개발 위험이 가장 작았다. FluidNC 등 ESP32 단독 구조는 향후 통합 로드맵으로 둘 수 있다.

**Q. 시각장애인 당사자 검증은?**

A. 현재 런북에는 "화면 가리고 완주" 합격 기준과 VoiceOver/TalkBack 병행 시나리오를 정의했다. 이후 실제 사용자를 대상으로 완료율, 평균 시간, 비상정지, 타임아웃 지표를 정량 측정한다.

## 7) 기대 효과
- 화면을 보지 않고도 가전을 끝까지 조작 가능 — "도와줄 사람이 있어야 쓸 수 있는 가전"을 "혼자 쓸 수 있는 가전"으로 바꾼다.
- 오조작/위험 상황 대응력 강화(이중 확인 + 즉시 비상 정지)
- 고가 스마트홈 교체 없이 기존 가전의 접근성을 개선 — 비용과 전자 폐기물을 동시에 줄인다.
