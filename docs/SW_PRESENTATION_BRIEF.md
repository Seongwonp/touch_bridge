## 3. 슬라이드별 재료

### 2번 — 문제

`docs/JUDGING_BRIEF.md` 1절과 `docs/BLIND_ASSOCIATION_RESEARCH.md` 참고.

핵심 논지 — **기존 대안이 왜 부족한가**를 짚는 게 설득력의 핵심이다:
- 점자 스티커·음성 안내는 **여전히 사용자가 정확한 위치를 직접 눌러야 한다**
- 스마트홈은 비용이 높고 **일부 기기만 호환**, 기존 가전은 버려야 한다
- 즉 "정보를 알려주는 것"과 "누를 수 있는 것"은 다른 문제다 → 여기가 우리 진입점

### 3번 — 해결 방식

구조도 한 장. 흐름은 이렇게:

```
사용자 발화 → [Flutter 앱] → [FastAPI 백엔드] → [AI 파싱]
                   ↓ 버튼 ID 시퀀스
              [BLE / ESP32] → 물리적으로 버튼을 누름
```

강조점: **가전을 교체하지 않는다.** 터치패드 위에 붙이는 장치가 사람 대신 누른다.

### 4번 — SW 아키텍처

| 층 | 기술 | 역할 |
|---|---|---|
| 앱 | Flutter / Dart | 접근성 UX, 음성 입출력, BLE 통신 |
| 백엔드 | FastAPI (Render 배포) | AI 프록시, 인증, 스키마 검증, 레이트리밋 |
| AI | 제공자 선택형 (`AI_PROVIDER`) | 자연어 → 버튼 시퀀스, Vision 버튼 매핑 |
| 장치 | ESP32 + BLE GATT | X/Y 이동 + 누름 |

백엔드 엔드포인트: `/parse-command`, `/vision-mapping`, `/device-profile/{id}`,
`/voice-command`, `/healthz` (`backend/main.py`)

**여기서 꼭 말할 설계 판단 하나 — API 키를 앱에 두지 않았다.**
앱이 AI 키를 직접 들고 있으면 디컴파일로 유출된다. 백엔드를 프록시로 두고
앱은 키를 모르게 했다. 백엔드에는 `X-API-Key` 인증 · 레이트리밋 ·
**AI 응답 스키마 검증**(`backend/validation.py`)이 있다. AI가 이상한 걸
돌려줘도 그게 곧장 기기 동작이 되지 않게 막는 층이다.

또 하나: AI 제공자가 환경 변수로 갈아끼워진다(`backend/ai_provider.py`).
학교 게이트웨이(`school_gateway.py`)와 범용 제공자를 코드 변경 없이 전환한다.

### 5번 — 음성 명령 파이프라인

단계별로 보여주면 좋다:

1. **STT** (`speech_to_text`) — 한국어 인식
2. **의도 라우팅** (`VoiceIntentRouter`) — 비상/도움말/상태질의/확인응답 판정
3. **간단 규칙** (`ApplianceCommandRouter`) — "30초 시작" 같은 빈출 명령은 AI 없이 즉시
4. **AI 파싱** — 규칙에 없으면 백엔드로. 자연어를 **버튼 ID 시퀀스**로 변환
5. **좌표 변환** — 버튼 ID를 기기별 매핑 프로필의 실제 X/Y(mm)로
6. **BLE 전송** → ESP32가 물리적으로 누름
7. **결과 안내** — TTS + 햅틱 + 화면

시연 예: `"햇반 3분 데워줘"` → `BT-03, BT-03, BT-03, BT-05` (1분 ×3 + 시작)
→ 4번 누름 → 3분 타이머 화면

**버튼 ID를 중간 표현으로 둔 게 설계 포인트다.** AI는 좌표를 모르고 논리 버튼만
안다. 기기가 바뀌면 매핑 프로필만 갈면 되고 AI 프롬프트는 그대로다.

### 6번 — 접근성 설계 (무게중심 ①)

"WCAG 준수했습니다"로 끝내지 말 것. **설계 결정**을 보여줘야 한다.

- **TTS 우선순위 계약** (`tts_service.dart`) — 스크린리더가 켜져 있으면 화면 이름 안내는
  억제하되, **결과·실패·비상 발화는 반드시 들리게** 우선순위를 명시하도록 계약을 고정했다.
  억제만 하고 대체 채널이 없으면 사용자에게 아무 정보도 안 남는다.
- **liveRegion 이중 채널** — TTS가 억제되는 상황을 대비해 `Semantics(liveRegion: true)`로
  상태 변화를 스크린리더 자체 채널로도 보낸다.
- **이중 탭 확인** — 위험한 동작은 두 번 탭. 단 스크린리더 사용 시 단순 화면 이동은
  OS의 확인과 중첩되지 않도록 앱 확인을 생략한다(`accessibility_confirmation_policy.dart`).
  **일괄 적용이 아니라 맥락별 판단**이라는 게 핵심.
- **색상 대비 자동 검증** — 테스트로 강제한다(`test/theme/app_colors_contrast_test.dart`).
  AA 4.5:1, 핵심 색상 AAA 7:1. 사람이 눈으로 확인하는 게 아니라 CI가 막는다.
- 준수 기준: WCAG 2.2 AA(핵심 색상 AAA), KS X 3253 (`docs/KS_X_3253_CHECKLIST.md`)

### 7번 — 안전 설계 (무게중심 ②)

이 프로젝트는 **물리적으로 버튼을 누르는** 시스템이다. 그래서 일반 앱과 다른 계약이 있다.

**(1) 거짓 완료 금지**
BLE write 성공은 **기기가 멈췄다는 뜻이 아니다.** 전송 성공과 ACK 확인을 구분해서,
기기가 정지를 확인(`STOPPED`)한 경우에만 "안전하게 중단" 화면으로 간다.
타임아웃이거나 무관한 센서 알림(`TEMP_OK`)이면 완료로 치지 않고 재시도하게 한다.
→ 화면을 볼 수 없는 사용자에게 "멈췄습니다"는 되돌릴 수 없는 신뢰의 문제다.

**(2) 순서가 안전 계약이다**
`'멈춰'`와 `'그만'`은 **부정 응답 토큰이면서 동시에 비상 정지 토큰**이다.
판정 순서가 뒤집히면, 확인 질문에 답하는 중 "멈춰"라고 했을 때 질문만 취소되고
**기기는 계속 돌아간다.** 그래서 비상 판정을 1순위로 두고, 최근에 이 순서를
`VoiceIntentRouter`로 분리해 **테스트로 고정**했다(24건).

**(3) 비상 정지는 어떤 흐름에서도 최우선**
3초 홀드 또는 음성. 3초 동안 진행 햅틱으로 경과를 촉각으로 알린다.

### 8번 — 품질 관리 (무게중심 ③)

> 이 슬라이드가 "SW 발표"에서 제일 차별화된다. 기능 나열이 아니라
> **엔지니어링 태도**를 보여주는 곳이다.

- 테스트 **392개** (Flutter 355 + 백엔드 37), 앱 라인 커버리지 **50.5%**
- 정적 분석 **경고 0건**을 `--fatal-infos`로 고정
- **GitHub Actions CI** — push/PR마다 analyze + 테스트 자동 실행 (`.github/workflows/ci.yml`)

**실제로 잡은 버그를 1~2개 구체적으로 말하면 설득력이 크게 올라간다:**

- *거짓 성공 안내* — 간단 규칙 명령의 신뢰도 값이 비어 있어 기본값 0.5로 읽혔고,
  저신뢰 분기에 항상 걸렸다. 결과적으로 `"1분 조리를 시작합니다"`라고 **말만 하고
  실제로는 아무 동작도 하지 않았다.** 화면을 못 보는 사용자에게는 거짓 성공 안내다.
  로그 분석으로 발견해 수정.
- *햅틱 타이머 누수* — 비상 정지를 한 번 쓸 때마다 1초 주기 타이머가 하나씩 누수돼,
  다음 사용 때 진행 햅틱이 중복 발화했다. 3초 경과를 촉각으로 가늠하는 신호가
  깨지는 접근성 문제. **테스트를 작성하다가 발견**했고, 수정을 되돌리면 테스트가
  실패하는 것까지 확인했다.

→ 메시지: **"테스트를 늘리니 실제 접근성 버그가 나왔다."**

## 4. 이 발표에서 하지 말아야 할 것

- **없는 숫자 만들기.** 사용자 테스트 결과, 성공률, 응답 시간 통계는 **측정한 적 없다.**
  `docs/USER_VALIDATION_PLAN.md`는 *계획서*이지 결과가 아니다. 그 문서 스스로
  "당사자가 검증하기 전까지는 접근성이 좋다고 단정할 수 없다"고 적어두었다 —
  발표에서도 같은 선을 지킬 것.
- **하드웨어를 완성된 것처럼 말하기.** HW는 전환 중이고 실기기 E2E 검증은 미완이다.
  데모는 BLE 데모 모드로 돌아간다 — 물어보면 정직하게 답할 것.
- **"AI가 알아서 합니다"로 뭉개기.** 심사진은 AI를 어떻게 **통제**했는지를 본다.
  스키마 검증, 버튼 ID 중간 표현, 간단 규칙 우선 처리가 답이다.

## 5. 예상 질문

| 질문 | 답변 근거 |
|---|---|
| AI가 잘못 해석하면? | 백엔드 스키마 검증 + 낮은 신뢰도 시 재확인 + 이중 탭 + 비상 정지 |
| 왜 AI 키를 백엔드에 뒀나? | 앱 디컴파일 시 키 유출. 프록시로 분리 + 레이트리밋 |
| 가전마다 버튼이 다른데? | 기기별 매핑 프로필(4점 투영 + 실제 mm). 버튼 ID는 논리 계층이라 AI는 그대로 |
| 시각장애인 테스트는? | **아직 안 했다.** 계획은 `docs/USER_VALIDATION_PLAN.md`. 현재는 표준 준수와 스크린리더 검증까지 |
| 커버리지 50%면 낮지 않나? | 안전 경로(비상 정지·음성 명령) 우선으로 올리는 중. 비상 정지 화면은 0% → 86% |
