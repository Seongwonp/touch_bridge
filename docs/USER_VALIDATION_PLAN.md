# Touch Bridge 당사자(시각장애인) 검증 계획

> 작성일: 2026-08-11 · M5 실행안 최신화: 2026-09-04
> 배경: Codex 접근성 리뷰 Part B 로드맵의 마지막 항목.
> 관련: [BLIND_ASSOCIATION_RESEARCH.md](BLIND_ASSOCIATION_RESEARCH.md) — 기관 연락처·인증 절차·법률·선행연구 상세 지금까지 세션에서 구현한
> 접근성 기능들(비상 정지 ACK 스푸핑 차단, 정직한 피드백, 인지부하 완화, 부엌
> 소음 대응, 보호자→사용자 인수 점검, 혼자 기기 등록)은 모두 개발자의 추정과
> Codex 리뷰만으로 만들어졌다. 실제 시각장애인 당사자가 검증하기 전까지는
> "접근성이 좋다"고 단정할 수 없다 — 이 문서는 그 검증을 어떻게 할지 정한다.

## 왜 필요한가

지금까지 이 프로젝트의 접근성 판단은 전부 비당사자(개발자 + AI 리뷰)가 내렸다.
스크린리더 문법이 자연스러운지, TTS 문구가 실제로 이해하기 쉬운지, 2단계 확인이
정말 필요한 곳에만 걸려 있는지는 당사자가 직접 써봐야만 알 수 있다. 특히 이
앱은 로봇팔이 물리적으로 버튼을 누르는 하드웨어와 연동되므로, UI 문제가 곧
안전 문제로 이어질 수 있다.

## 검증 대상

- **최우선**: 전맹(全盲) 또는 저시력으로 TalkBack/VoiceOver를 일상적으로 쓰는
  성인 2~3명. 스마트폰 사용에 익숙할 필요는 없다 — 오히려 초보 사용자가
  섞여야 온보딩 난이도를 제대로 검증할 수 있다.
- 가능하면 아래 두 그룹을 나눠서 본다. 둘의 요구가 다르다.
  - **혼자 쓰는 사용자**: 보호자 없이 기기를 등록하고 음성으로 제어하는 그룹
    (이번 세션에서 만든 "기기 추가하기 → 사진 없이 좌표로 설정" 경로 대상).
  - **보호자와 함께 쓰는 사용자**: 보호자가 사진 매핑으로 설정하고
    `GuardianHandoffScreen` 인수 점검을 거쳐 넘겨받는 그룹.
- 섭외는 개인적 인맥이나 지인 추천에 의존하지 말고, 시각장애인복지관·
  점자도서관·시각장애인동문회 등 기관을 통해 공식적으로 요청한다. 실제
  기기(로봇팔)가 오작동할 가능성이 있으므로 반드시 보호자/감독자 동석 하에
  진행하고, 참여자에게 로봇팔이 손 닿는 범위에서 작동한다는 점을 사전에
  명확히 고지한다.

### 모집군 분리

결과를 한 집단으로 합치지 않는다. 최소 모집 목표는 전맹 3명, 저시력 3명이며,
두 군 모두 Android TalkBack과 iOS VoiceOver 사용자가 가능하면 한 명 이상
포함되게 한다. 표본 수가 부족하면 통계적 일반화 대신 문제 발견형 사용성
평가로 명시한다.

| 모집군 | 주 입력 방식 | 별도 확인 항목 |
|---|---|---|
| 전맹 | 화면읽기 + 음성 + 햅틱 | 초점 순서, 중복 확인 횟수, 음성만으로 복구 가능 여부 |
| 저시력 | 확대 + 고대비 + 음성 보조 | 200% 글자, 대비, 잘림, 버튼 크기와 거리 |

보호자 설치와 사용자 실행도 별도 역할로 기록한다. 한 참여자가 두 역할을 모두
수행하면 학습 효과가 섞이므로 실행 순서를 남기고 결과 해석 시 구분한다.

## 검증 방법

- **진행 방식**: 대면, 참여자 자택 또는 접근성이 확보된 공간에서 실기기로
  진행. 화면 공유나 원격 테스트는 로봇팔 안전 문제 때문에 지양한다.
- **관찰자 역할**: 진행자는 시나리오만 읽어주고 조작법을 알려주지 않는다.
  참여자가 스스로 TTS 안내만으로 다음 행동을 찾아내는지가 핵심 측정 대상.
  막히면 즉시 개입하지 말고 최대 30초 대기 후 필요한 최소한의 힌트만 준다.
- **기록**: 각 태스크마다 (1) 완료 여부 (2) 개입 필요 여부와 개입 시점
  (3) 참여자가 헷갈려한 TTS 문구/화면 (4) 소요 시간을 기록한다. 녹음은
  참여자 동의 하에만 진행하고, 즉시 식별 정보를 제거한 메모로 남긴다.

## 시나리오별 태스크 (이번 세션 구현 기능 대응)

1. **최초 기기 등록 (혼자)** — 앱을 처음 켠 상태에서, 보호자 도움 없이
   전자레인지를 등록해보라고 요청한다. 홈 빈 화면 → "기기 추가하기" →
   블루투스 연결 → "사진 없이 좌표로 설정" → 조이스틱/테스트 눌러보기로
   버튼 위치 확정까지 스스로 도달하는지 확인한다.
2. **보호자 핸드오프 신뢰** — 보호자 역할로 사진 매핑을 마친 뒤,
   `GuardianHandoffScreen` 점검 결과를 실제 사용자에게 넘긴다. 사용자가
   "정말 준비됐다"는 확신을 갖는지, 아니면 여전히 불안해하는지 인터뷰.
3. **음성 명령 오인식 복구** — 일부러 소음이 있는 환경(부엌 소음 대응
   기능 대상)에서 "삼십초 시작해줘"를 발화시키고, 신뢰도가 낮게 잡혔을 때
   재확인 질문("~라고 들었어요, 맞으면 다시 한 번 말씀해 주세요")을 참여자가
   자연스럽게 이해하고 응답하는지 확인.
4. **다시 듣기** — 안내를 놓쳤을 때 "다시 말해줘"가 직관적으로 나오는
   발화인지, 아니면 다른 표현을 기대했는지 확인한다.
5. **비상 정지** — 음성 "멈춰"와 화면의 비상 정지 버튼 둘 다 시도하게 하고,
   정지 확인 음성 안내가 나올 때까지 걸리는 체감 시간과 신뢰도를 확인.
6. **숫자 패드 vs 시작 버튼의 확인 절차 차이** — 원격 제어 화면에서 숫자
   입력은 1단계, "시작"은 2단계(누르고 확인)로 다르게 만들었는데, 참여자가
   이 차이를 "왜 다른지" 스스로 이해하는지, 아니면 일관성 없다고 느끼는지
   확인한다. 이 항목은 설계 가정이 틀렸을 가능성이 있는 곳이라 특히 주의
   깊게 듣는다.

## 성공 기준

- 태스크 1(혼자 등록)은 **개입 없이 완료**가 목표다. 이게 안 되면 이번
  세션에서 만든 "혼자 등록" 경로 자체가 실패한 것이므로 최우선으로
  재설계한다.
- 나머지 태스크는 완료 여부보다 "어디서, 왜 막혔는지"가 더 중요한
  산출물이다. 완료율을 KPI처럼 취급하지 않는다.
- 참여자 3명 중 2명 이상이 동일한 지점에서 막히면 그 지점은 설계 결함으로
  간주하고 우선 수정한다.

## 검증 후 처리

- 발견된 문제는 `docs/WORK_LOG.md`에 이 문서를 인용해 기록하고, 재설계가
  필요하면 `docs/ACCESSIBILITY_REDESIGN_PLAN.md`에 새 항목으로 추가한다.
- 참여자 피드백 원문(개인정보 제거 후)은 이 문서가 아니라 별도
  비공개 메모로 보관한다 — 이 문서는 계획이지 결과 저장소가 아니다.
- 검증은 1회성이 아니라, 큰 흐름(온보딩, 매핑, 음성 제어)이 바뀔 때마다
  최소 1명 이상과 재검증하는 것을 원칙으로 한다.

## M5 과업 및 기록 양식

각 참여자에게 아래 과업을 같은 순서로 강요하지 않고 순서를 교차 배정한다.
화면 이동, 촬영 정렬 안내, 모서리/버튼 미세 조정, 기기 명령, 취소, 비상 정지를
각각 독립 과업으로 측정한다. 촬영 안내는 현재 실시간 자동 판정이 아닌
수동 4단계 방향 안내라는 점을 진행자가 사전에 고지한다.

| 필드 | 기록 값 |
|---|---|
| 참여자 코드 | 익명 코드, 장애 유형·OS·화면읽기 숙련도 별도 기입 |
| 역할/과업 | 보호자 설치 또는 사용자 실행, 과업 번호 |
| 성공 여부 | 무개입 성공 / 힌트 후 성공 / 실패 / 안전 중단 |
| 시간·조작 수 | 시작~완료 초, 탭/되돌아가기/재시도 횟수 |
| 안전 결과 | 오작동, 잘못 누른 버튼, 비상 정지 성공 및 ACK 시간 |
| 접근성 문제 | 초점 손실, 중복 낭독, 글자 잘림, 진동 구분 실패 |
| 참여자 발화 | 동의받은 비식별 요약만 기록 |
| 후속 조치 | 이슈 ID, 심각도, 수정 버전, 재검증 결과 |

중단 기준은 손이 이동부에 접근함, 원점/위치 오류, 예상 밖 기기 작동, 참여자의
즉시 중단 요청이다. 이때 성공률보다 안전 중단이 올바르게 작동했는지를 우선
기록한다. 실제 모집·평가가 끝나기 전에는 M5의 당사자 검증 항목을 완료로
표시하지 않는다.
