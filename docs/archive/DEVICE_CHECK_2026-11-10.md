# 실기 TalkBack 점검 기록 (2026-11-10)

이 문서는 **현재 브랜치에 구현된 흐름**을 검사한다. 재설계 제안(`docs/USER_FLOW_REDESIGN_PROPOSAL.md`)의 실행 확인 화면, 조리 취소, 앱 두 번 누르기 제거는 아직 구현 전이므로 합격 기준이 아니다(5절에 따로 둔다).

**기록 구분**: 하드웨어 없이(데모 모드 포함) 확인한 항목은 결과 칸에 **[앱 동작]**, 실제 ESP32·Bot과 묶어 확인한 항목은 **[실기]**로 적는다. 데모 모드의 "성공"은 전송 성공을 흉내 낸 것이다.

## 2. 기록 형식

항목마다 아래를 적는다. 판정은 통과 / 실패 / 확인 못 함 중 하나다.

- 조작 순서: 실제로 한 제스처를 순서대로 적는다(예: 오른쪽 넘기기 3번 → 두 번 탭)
- 들린 안내: TalkBack 낭독과 앱 음성을 구분해 그대로 적는다
- 발생한 동작: 화면 전환, BLE 전송(통신 로그), 펌웨어 로그, 모터·Bot의 실제 움직임, 전자레인지 상태를 각각 따로 적는다. 로그는 물리 동작의 증거가 아니다
- 판정과 메모

## 3. 현재 구현 흐름 점검

| # | 항목 | 현재 구현에서 기대하는 동작 | 결과 |
|---|---|---|---|
| A1 | 홈 진입 | 첫 포커스와 읽기 순서로 현재 기기와 '말하기'를 찾을 수 있다 | |
| A2 | 기기 전환 | 하단 이전·다음 버튼으로 바꾸고, 바뀐 기기 이름이 들린다(리뷰에서 안 들릴 수 있다고 지적됨) | |
| A3 | 음성 화면 진입 | TalkBack에서 마이크 버튼을 한 번 활성화하면 바로 녹음이 시작된다(앱 확인 탭 없음, `7893ed8`) | |
| A4 | 명령 "30초 돌려줘" | 현재 계약대로 확인 없이 누르기로 진행하고, 누르기 전에 무엇을 누르는지 들린다 | |
| A5 | 확인이 필요한 명령 | 예: 음식 이름. 확인 질문이 들리고 "예"로 실행, "아니요"로 취소된다 | |
| A6 | 누르는 중 화면 | '즉시 정지'를 몇 번 넘겨서 찾는지 센다. 단일 활성화로 정지 요청이 나간다 | |
| A7 | 남은 시간 화면 | 값이 "2분 30초"처럼 읽힌다. 안내가 "두 번 탭하세요"로 들린다 | |
| A8 | 남은 시간 화면 정지 | '비상 정지'를 TalkBack 두 번 탭으로 활성화하면 바로 정지 요청이 나간다(`7893ed8`) | |
| A9 | 정지 결과 | ACK가 오면 "터치브릿지를 멈췄습니다. 가전이 이미 돌고 있으면…"이 들린다. "안전합니다"는 들리지 않아야 한다 | |
| A10 | 시간 종료 결과 | "설정한 시간이 지났습니다. 가전이 멈췄는지 확인해 주세요"가 들린다 | |
| A11 | 예시 명령 칩 | 첫 활성화에는 "한 번 더 누르면 실행합니다"만 들리고 아무것도 전송되지 않는다 | |
| A12 | 설정 | 슬라이더가 "말하기 속도, 보통"처럼 이름과 값으로, 스위치가 이름과 켜짐 상태로 읽힌다 | |
| A13 | 기기 등록 | 연결 성공·실패와 홈 추가 결과가 TalkBack 사용 중에도 들린다 | |

## 4. 반드시 볼 위험 항목

| # | 항목 | 방법 | 결과 |
|---|---|---|---|
| R1 | **사용자 발화 없는 정지** | 남은 시간 화면(마이크 켜짐)에서 말하지 않고 TalkBack 포커스만 '비상 정지' 버튼과 "멈추려면…" 안내 글자로 옮긴다. 같은 조작을 5번 반복해 정지가 몇 번 일어나는지 센다. 결과는 "이 환경에서 5회 중 N회"로 적는다. 0회여도 오인식이 없다고 확정하지 않는다 | |
| R2 | 진입 안내와 마이크 | 남은 시간 화면에 들어갈 때 TalkBack이 화면을 읽는 동안 정지가 일어나는지 본다. 앱 TTS 대기는 TalkBack 낭독을 기다리지 않는다 | |
| R3 | 녹음 중 낭독 | 음성 화면에서 녹음이 시작될 때 "듣고 있습니다" 같은 낭독이 인식 결과에 섞이는지 본다(화면의 인식 문장 확인) | |
| R4a | **연결 끊김 → 재시도 (누르는 중 화면)** | 누르는 중에 ESP32 전원을 끄고 '즉시 정지'를 활성화한다. 들린 안내가 실제 원인(연결 없음, 전송 실패, 응답 미확인 중 무엇)과 맞는지 적는다. 타이밍에 따라 다르게 나올 수 있으므로 특정 문구를 기대하지 않는다. 그다음 이 화면의 **'다시 정지'** 버튼을 몇 번 넘겨 찾았는지, 혼자 활성화할 수 있었는지 적는다 | |
| R4b | **연결 끊김 → 재시도 (남은 시간 화면)** | 남은 시간 화면에서 ESP32 전원을 끄고 '비상 정지'를 활성화한다. 안내가 원인과 맞는지 적는다. 이 화면에는 '다시 정지' 버튼이 없다. 실패 뒤 **같은 '비상 정지' 버튼**으로 다시 시도할 수 있는지 확인한다(코드상 실패 시 `_stopInProgress`를 풀고 마이크를 다시 연다) | |
| R4c | **ACK 미응답 (두 화면 각각)** | BLE 연결과 명령 수신은 유지하고 정지 응답만 보내지 않는 **시험용 펌웨어**로 검사한다(6절). 기대: "중단 명령을 보냈지만 응답을 확인하지 못했습니다…"가 들리고, 완료 화면으로 넘어가지 않으며, R4a·R4b와 같은 버튼으로 재시도할 수 있다 | |
| R4d | **실패 뒤 상태 다시 읽기** | R4a~c마다, 실패 안내가 끝난 뒤 TalkBack으로 화면을 다시 훑어 지금 상태(정지 실패·미확인)를 읽을 수 있는지 적는다. 코드 확인 결과, 누르는 중 화면은 결과 문장을 화면에 남기지만 **남은 시간 화면은 실패 문장을 음성으로만 내고 화면에 남기지 않는다. 이는 이미 수정 대상이다.** 실기에서는 사용자가 겪는 영향(다시 읽을 수 없어 상태를 모르는지)을 기록한다 | |
| R5 | 중복 낭독 | 결과 안내가 앱 음성과 TalkBack으로 두 번 들리는지, 서로 끊는지 적는다 | |
| R6 | 부분 인식 정지 지연 | "멈춰"라고 말한 뒤 정지 요청까지 걸린 시간을 대략 잰다. 나중에 최종 인식만 받을지 정하는 근거로 쓴다 | |

## 5. 재설계 후 검사할 항목 (지금은 검사하지 않음)

- 모든 가전 실행이 실행 확인 화면(실행·취소, 네·아니요)을 거친다
- 앱 자체 두 번 누르기가 어떤 화면에도 없다
- 조리 취소: 기기별 취소 매핑·연결·위치·정지 원인 조건, 확인 근거별 안내 문구
- 안내 담당 표대로 자동 낭독이 한 번만 나고, 상태·결과를 다시 탐색해 읽을 수 있다
- 홈 기기 선택이 세로 목록이다

## 6. 시험용 펌웨어 (R4c 전용)

- 목적: 연결과 명령 수신은 그대로 두고, 정지 응답(`STOPPED`)만 BLE로 보내지 않는다. 정지 동작 자체(`emergencyStop()`)는 그대로 실행한다.
- 방법: 저장소가 아닌 로컬 복사본(`C:\pio-build\tb_corexy_noack`)에서만 `out()`이 `STOPPED`가 든 줄을 BLE로 보내지 않게 막는다(USB 시리얼에는 그대로 찍는다. 이 줄은 펌웨어가 정지 처리를 수행했다는 기록일 뿐 물리적으로 멈췄다는 증거가 아니다). 컴파일 플래그 `TB_TEST_SUPPRESS_STOP_ACK`로 켠다.
- 시험 조건 확인(빌드 성공만으로는 확정하지 않는다):
  - 정지 전후로 BLE 연결이 유지되는지(앱 연결 상태, 일반 명령 응답)
  - 앱이 정지 ACK로 인정하는 응답(`STOPPED`, 단독 `ok`, `stop`으로 시작하는 줄)이 BLE 로그에 하나도 오지 않는지(앱의 통신 로그 화면으로 확인)
  - 모터와 Bot의 실제 움직임, 전자레인지 작동 상태는 USB 로그와 별개로 눈으로 관찰해 각각 적는다
- 주의: **이 펌웨어는 저장소에 커밋하지 않고, 시험이 끝나면 즉시 정상 펌웨어로 다시 굽는다.** 시연·실사용에 쓰지 않는다. 기록에는 R4c를 이 펌웨어로 했다고 적는다.
- 복구 확인: 정상 펌웨어를 다시 구운 뒤 정지를 한 번 해서 정지 ACK가 다시 수신되고 완료 화면으로 넘어가는지 기록한다.
